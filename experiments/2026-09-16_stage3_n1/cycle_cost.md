## How the chain is assembled

* **Age gate convention.** The recent tier holds at most `a` dense lineages, i.e. v31
  run with `gens = a` (metered whole, including every non-tower cost of the chain).
  At the end of layer `l` the lineage born at `l - a` is **joined** instead of dropped.
  Depth 16 gives `15 - a` joins (the first is the basis init), `14 - a` old D21+D3
  queries, 1 old D3-only query (last layer), `15 - a` transports. Under the other
  reading ("merged when it reaches age a") read this table's `a - 1` column.
* **Old tier** per layer: transport `V <- diag(w1) W^T V`; query
  `X = einsum('ijk,ai,aj->ak', G, V, V)`, `D3 = sum(X*V)`, `D21 = (X @ V^T) * off_mask`,
  added into the recent slices. Schedules:
  * `qr_every_k`: QR of V + core rotation `G(R,R,R)` at every k-th join layer; joins on
    rebased layers project with `V^T`, the others with the oblique projector
    `solve(V^T V, V^T)`. `qr_never` = oblique every join.
  * `join_b_sS`: every join is sketch (`P Om + A_L Om`, s columns) → QR of `[V, Y]`
    (n, r+s) → `G(Rv,Rv,Rv)` extension → project lineage into U → mode Gram `Gu Gu^T`
    → `eigh` → keep top r → `V = U E`, `G = Gx(E,E,E)`. Re-orthonormalises by
    construction, so no separate schedule.
* **Join core spelling** (cheapest metered): `aD = p d(sb) + 3 aL d(eb) + z L^T`,
  `E = einsum('ij,kj,lj->ikl', p, p, aD)`, `H = einsum('ij,kj,lj->ikl', aL, aL, p*w2)`,
  `G += sym3(E/3 + H)` (the L block collapses to 3 placements because `C_L = A_L d(w2)`).
* Whole chain C/B = metered v31(gens=a) + counts × metered step costs. For each role
  the cheapest metered spelling is used (FLOPs), see "chosen spellings".
* `symdeclared = True` additionally lets the query/rebase read the core through
  `flopscope.as_symmetric(G, symmetry=(0,1,2))` (wrap + validation billed inside the
  step, every layer). It is a documented meter feature that halves the query; it is a
  separate row set because its server behaviour and residual (local flopscope overhead
  0.12–0.22 s per call at r=128–150) are unverified.

## Self-check (float64, n = 12) — PASS, worst relative error 2.2e-14

* the lineage-tensor definition equals v31's own `_dslice3` / `_dslice21` (4e-16, 3e-16);
* both query spellings equal a dense `einsum` of `G(V,V,V)` for random symmetric G and
  non-orthonormal V (1.8e-15);
* join (a) at full rank, ortho and oblique, einsum and KR: `G(V,V,V)` equals the dense
  lineage tensor and its D3/D21 equal v31's slices (≤ 2.2e-14);
* transporting (V, G) equals v31 `_advance` + `_wick_tower` then slices (2e-15);
* rebase (both spellings) preserves `G(V,V,V)` (4e-15);
* join (b): at r+s = n it reproduces old + new exactly (3e-15); truncated to r=8 it
  equals the total projected onto span(V_new) in each mode, V_new orthonormal (3e-15).

## Headline

* **No-merge reference:** metered v31 = 661,961,586,226 FLOPs = **0.30103 B**, 13,052
  operations; graded 0.3010 → discrepancy +2.5e-5 B (the grader's own +2^25 offset is
  1.5e-5 B). Identical to the stored v31 certification count. (v31's internal budget
  guard formula says 0.475 B; it is a deliberate over-predictor.)
* **Recent tier alone** (gens = 2/3/4/5): 0.0859 / 0.1179 / 0.1470 / 0.1738 B. Each
  extra dense lineage costs ~0.03 B, which bounds the achievable saving.
* **Operations are never binding**: every configuration is 12,500–13,600 (gate 22,000).
  The old tier adds only ~350–900 operations.
* **Configurations at ≤ 0.20 B:**
  * fixed-basis joins (a): r=96 all a≤5; r=128 a≤3 (a=4 with qr_every_2/4/never);
    r=150 only a=2 (a≤3 with symdeclared). Cheapest: r=96, a=2, qr_never 0.1127 B
    (0.1075 symdeclared).
  * **basis-enlarging joins (b), the only variant that can admit new directions:**
    r=96 with s=32 at a≤4 (0.141/0.169/0.194), s=48 at a≤3, s=64 at a=2 only.
    **Nothing at r ≥ 128** (best r=128 is 0.2035 B at a=2, s=32).
* **Dominant cost** in every merged configuration is the **join**: the two
  `(m,n)^3` einsums building the projected lineage core (~2 n m^3 each, with m = r+s),
  then for (b) the two dense `(r,r,r)`-with-`(m,r)` rotations/truncations (~2 m^3 r each)
  and the mode Gram (2 m^4). The per-layer query (≈ 2 n r^3; ≈ n r^3 symdeclared) is
  second. Transport (≤ 2.4e-4 B) and QR (<1% of a rebase) are negligible; the rebase
  cost is the O(r^4) core rotation (6 r^4). The fixed-basis total is essentially
  `recent(a) + (15-a)(join ≈ 4 n r^3) + (14-a)(query ≈ 2 n r^3)`.
* **Memory:** largest per-step tracemalloc increment is 1.3 GiB (join_b, r=256, s=128);
  ≤ 0.35 GiB for every r ≤ 150 step. v31 whole-chain process peak working set 3.4 GiB
  (no-merge) and 0.86–1.47 GiB at gens 2–5. LAPACK workspaces are not in tracemalloc.
  All far under 8 GiB.
* **Local wall (ADVISORY, never an authority):** the flopscope overhead of einsum steps
  is not negligible: join_b r=96 s=32 ≈ 0.08 s/join and r=128 ≈ 0.11 s/join locally,
  against v31's whole-chain local flopscope overhead of 2.6 s (graded residual 0.14 s).
  An r=96–128 join_b tier could add ~50% to residual; this must be measured with the
  subprocess runner, not inferred from operation counts.

## NOT priced

* **Any output-aware / relevance basis** (Jacobian of final mean with respect to old
  state, covariance/birth-weighted Grams, the generalized PSD problem in the plan's
  direction A). Backpropagating a final-layer relevance through L layers is
  O(L n^3) for a dense Jacobian (≈ 0.001 B per (n,n)@(n,n), i.e. ≈ 0.016 B per extra
  dense sweep of 16 layers) or O(L n^2 q) for q probe directions; a weighted Tucker
  truncation adds O(n^2 r) per mode Gram plus O(r^3) eigensolves per join.
* Power iterations in the range finder (each +2 n^2 s per leg, +QR 2 n (r+s)^2); column
  norm/argsort sketch selection (v31-style) instead of a dense Omega.
* Cheaper exact variants not metered: exploiting `Rv = [R11; 0]` to rotate in r
  instead of m (saves most of join_b's rotation einsum); projecting only the new
  s directions; declaring the join cores symmetric; rank-adaptive r.
* Float32 conditioning safeguards for `qr_never` / oblique projection after 10+
  transports (priced as a single `solve`; its numerical adequacy is unassessed).
* Accuracy of any configuration (fixed-basis join (a) cannot represent directions
  outside the init sketch's transported span; truncation error; K4 interaction).
* Server residual wall and the Linux 8 GiB enforcement.
* The +2^24/2^25 server FLOP offset (≈1.5e-5 B, immaterial here).
